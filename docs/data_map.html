Ingestion#

A note enters the corpus only after path, encoding, frontmatter and content checks. This policy is shared by indexing rather than delegated to a model.

  1. Discover *.md recursively in sorted path order.

    Sorting makes duplicate-ID handling deterministic: the first path wins.

  2. Reject paths Obsidian does not treat as normal notes.

    Any hidden parent, configured skip directory, .trash, .obsidian, Templates, and Excalidraw Markdown are excluded.

  3. Decode strictly as UTF-8.

    A non-UTF-8 file is skipped instead of silently embedding replacement characters.

  4. Split frontmatter from body; normalize tags and dates.

    Title falls back to the filename. Identity uses frontmatter id when available, otherwise a stable path-derived identity.

  5. Reject body or frontmatter tagged #ignore / #secret.

    The ignore-tag vocabulary is configurable. Exclusion occurs before chunking or any provider call.

  6. Emit a normalized note record.

    note_id, path, title, tags, created, updated, date, type, provenance, body plus a SHA-256 of the original file.

Nothing excluded here is embedded, sent to reranking, included in synthesis context, or offered as an enrichment neighbor.

Chunking#

Production chunking is deterministic, Markdown-aware and based on a model-independent token estimate. The 450-token target is descriptive; current packing decisions are driven by the 300, 600 and 900-token boundaries.

The estimator counts each word run and punctuation mark as one token; CJK characters count individually. It is a stable budgeting heuristic, not a provider tokenizer. The legacy character-window splitter exists only when a caller explicitly supplies max_chars; normal sync does not.

Index views#

Each indexed entry has three related text views. Keeping them separate prevents retrieval-only context from leaking into cited evidence.

Dense / rerank text

  • # title + pathDocument entries also include tags and date.
  • Section descriptorNearest enclosing heading only. Heading path and parent ID are stored as metadata but kept out of this text: a wider provenance preamble was measured here and cost more than it returned.
  • Optional note summaryOne canonical note-level summary, loaded from the sidecar and repeated in each derived entry.
  • Original note body or chunk sourceThis complete representation is embedded; thorough rerank sees the same stored document.

BM25 text

  • Rebuilt from metadata + sourceDoes not blindly reuse the dense document.
  • Lowercase word tokensSmall built-in stop-word removal, then Porter stemming.
  • Context excluded by defaultIncluded only when contextual_bm25: true.
  • Parametersk1 = 1.2, b = 0.75.

  • Document → original bodySection → exact chunk text.
  • Drives must-include filters and excerptsQuoted evidence is source-addressable.

Retrieval context#

Context is one optional summary per note. Its canonical sidecar record is the source of truth; Chroma receives disposable derived copies for dense retrieval and reranking. There is no per-chunk summary generation or separate context cache.

Manual authoring — default strategy

  1. Prepare a self-contained job.

    Title, full body, heading outline, immutable source fingerprint and instructions; the summary starts empty.

  2. Generate roughly 60–100 factual words.

    The authoring agent is told to use only note claims and preserve every other job field.

  3. Validate, then atomically promote the batch.

    Schema, hashed filename, ID, title/body fingerprint, non-empty normalized text and 1,200-character maximum are checked before the first canonical write.

  4. Sync notices a ready or changed record automatically.

    No --contextualize flag is needed. Missing or stale summaries never cause a chat call and never block source indexing.

OpenRouter authoring — optional strategy

  1. Resolve the same canonical sidecar first.

    A ready manual or OpenRouter record is reused without a model call.

  2. Generate once for each missing or stale note.

    The model sees the note title, heading outline and body under a 12,000 estimated-token prompt ceiling—not individual chunk requests.

  3. Require exactly {"summary": "…"}.

    Temperature 0, 400 output-token ceiling; the same normalization and 1,200-character record limit apply.

  4. Write the successful result to the sidecar before embedding.

    Generation failure still indexes current source without a summary and is retried on the next sync. --refresh-context forces every note to regenerate.

The canonical record is keyed by note ID and stores schema version, source fingerprint, title, summary, generator identity/model and timestamp. The fingerprint covers schema version + title + body, but excludes path and timestamps: a move reuses the summary, while a title/body edit makes it stale. Changing only the summary changes its context key and causes affected Chroma entries to be rebuilt.

Mixed retrieval searches sections and returns source-addressable sections, capped at three per note so one long note cannot crowd out the rest.

RRF(d) = 0.5 / (60 + semantic_rank(d)) + 0.5 / (60 + keyword_rank(d))
freshness(d) = exp(−age_days / 365)  ∈ [0, 1]
λ_q = s(k) − s(k+B)  (relevance spanning B ranks at the cutoff)
final(d) = relevance(d) + λ_q × freshness(d)

RRF components and the fused score are min–max scaled for output. Equal-valued series map to 0.5. Stable sorting and sorted candidate IDs make tie behavior deterministic. Recency adds to the reranker’s own scores rather than replacing them, and its budget λ_q is read from the score gaps straddling the result cutoff. B (recency_rank_budget, default 1) is therefore a promotion allowance in rank positions, and recency strength does not change with the rerank pool size. Set recency_strategy: multiplicative for the pre-2026-07 blend.

Synthesis#

Retrieval results become a compact evidence packet. The answer model does not see the vector/BM25 machinery and cannot cite retrieval-only context.

  1. Take candidates in final rank order.

    Default cutoff is 8, configurable by n-context.

  2. Assign local citation keys S0….

    Each block contains final score, title, path and the first 700 source characters. Only distilled, reference and llm provenance are explicitly marked; unmarked notes are explained to the model as the user’s own writing.

  3. Request one JSON answer using only those blocks.

    Every factual claim should cite a local key. Insufficient evidence must produce an abstention and state what is missing.

  4. Repair harmless JSON framing or truncation where possible.

    Code fences, surrounding chatter and mechanically closable truncated JSON can be recovered.

  5. Validate semantic fields fail-closed.

    Non-object output, non-string answer, non-boolean abstention, or an empty non-abstained answer becomes an abstention. Invalid confidence becomes low.

  6. Resolve citations only against the packet.

    Unknown and duplicate keys are removed. Long uncited sentences produce warnings.

Saving is a separate quality gate: no file is created for an abstention, low confidence, empty answer, absent citations, or an existing target. A saved answer is marked provenance: distilled and remains a regenerable pointer to raw sources.

Enrichment#

Enrichment is a neighborhood-based proposal pipeline. It never writes the note or index; a human or agent applies accepted fields through the guarded mutation commands.

Neighbor construction before the planner model

deterministic + retrieval
  1. Normalize the target note.

    For an existing note: split frontmatter/body and choose explicit title → frontmatter title → first heading/line → filename. For stdin: body plus optional title and no current path.

  2. Run up to three fast document queries.

    Title: first 100 characters. Body: first 300 characters. Terms: five most frequent stemmed, non-stop-word body tokens.

  3. Merge by note ID with cross-query RRF.

    Each channel contributes 1/(60 + rank). The target note is removed; malformed/non-finite candidates are ignored; keep at most 15.

  4. Replace generic prefixes with focused source sections.

    Embed title + body capped at 8,000 characters, search all sections belonging to the 15 neighbor notes, and keep the first/best section per neighbor.

  5. Show the planner a compact neighborhood.

    Each neighbor contributes title, path, discovery channels, best heading and a 750-character stored section excerpt.

Placement suggestion

  • If the note is from stdin or currently in an inbox-like folder, use a folder only when at least 3 of the top 5 neighbors share it.
  • stdin without consensus → Inbox/<title>.md.
  • Existing non-inbox note → keep its current path.

Plan output

  • Title + whether it materially changed
  • Suggested path
  • Patch limited to type, aliases, supplied source_url
  • Validated inline insertions and related candidates
  • Warnings and overall confidence

provenance is never proposed by enrichment. The creation flow sets it; once set, it is immutable. Applying any accepted plan is a separate, explicit Obsidian-CLI mutation.

Trust boundaries#

  • Vault text is untrusted input. Chat prompts explicitly tell models to ignore instructions contained in notes, context and neighbors.
  • Note summaries affect discovery, not evidence. The stored source_offset reconstructs source-only text for excerpts and must-include checks.
  • Provider arrays are alignment-sensitive. Missing, duplicate, out-of-range, non-finite or dimensionally inconsistent embedding/rerank results fail instead of being zipped onto the wrong entries.
  • Filters precede candidate ranking. Folder, tag, type, provenance, dates and must-include conditions define the eligible universe.
  • Model proposals are never mutation authority. Synthesis saving has quality gates; enrichment only returns a plan; normal note changes go through the running Obsidian app.
  • Raw human notes outrank regenerated summaries on conflict. Distilled notes are pointers; imported reference/LLM notes are labeled for the answer model.
